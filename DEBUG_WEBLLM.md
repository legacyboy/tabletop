# Debug: "Failed to construct 'URL': Invalid URL" in the WebLLM (in-browser) path

## TL;DR

There are **two** layered bugs in the offline WebLLM path. The first (the literal
`Invalid URL` TypeError) was already fixed in commit `4b24772`, but that fix only
moved the failure one step further. The second, still-present bug is that WebLLM's
`cleanModelUrl()` rewrites the local model path into a HuggingFace `resolve/main/`
layout, but the vendored model files are stored **flat**, so every model-file
fetch 404s. The fix: store model files under `resolve/main/` (mirroring the
HuggingFace layout WebLLM expects).

## Root cause 1 — `Invalid URL` (already fixed, kept for context)

`vendor/webllm/index.js` line ~9462:

```js
function cleanModelUrl(modelUrl) {
    modelUrl += modelUrl.endsWith("/") ? "" : "/";
    if (!modelUrl.match(/.+\/resolve\/.+\//))
        modelUrl += "resolve/main/";
    return new URL(modelUrl).href;   // <-- single-arg new URL()
}
```

`cleanModelUrl()` calls `new URL(modelUrl)` with **no base URL**. When the model
record's `model` is a root-relative path like `/vendor/models/gemma3-1b-it-.../`,
`new URL()` throws exactly:

```
TypeError: Failed to construct 'URL': Invalid URL
```

`app/js/providers/webllm.js` now resolves `model`/`model_lib` against
`location.origin` before handing the `appConfig` to `CreateMLCEngine`, so
`cleanModelUrl()` receives an absolute `http(s)://` URL and no longer throws.
That part is correct and still necessary.

## Root cause 2 — `resolve/main/` path mangling (THE REMAINING BUG)

`cleanModelUrl()` is written for **HuggingFace repo URLs only**. For any URL that
is not already a HF `.../resolve/.../` URL it appends the literal string
`resolve/main/`. So the absolute model URL:

```
http://localhost:8000/vendor/models/gemma3-1b-it-q4f16_1-MLC/
```

becomes:

```
http://localhost:8000/vendor/models/gemma3-1b-it-q4f16_1-MLC/resolve/main/
```

WebLLM then fetches `mlc-chat-config.json`, `tokenizer.json`, `tensor-cache.json`,
and `params_shard_*.bin` from that `resolve/main/` directory (the tensor cache's
`dataPath` fields are relative, and `mlc-chat-config.json`'s `tokenizer_files` are
relative, so everything is resolved against the same cleaned `modelUrl`).

The problem: `scripts/vendor-offline.sh` downloaded those files **from**
`https://huggingface.co/mlc-ai/<id>/resolve/main/<file>` but stored them **flat**
at `vendor/models/<id>/<file>`, dropping the `resolve/main/` segment. So every
fetch from `.../resolve/main/...` returned 404.

Verified with Node (reproduces `cleanModelUrl` exactly):

```
"/vendor/models/gemma3-1b-it-q4f16_1-MLC/"                        => THROWS "Invalid URL"  (pre-fix)
"http://localhost:8000/vendor/models/gemma3-1b-it-q4f16_1-MLC/"   => .../resolve/main/       (post-fix, wrong path)
"https://huggingface.co/mlc-ai/gemma3-1b-it-q4f16_1-MLC"          => .../resolve/main/       (what WebLLM expects)
```

## The fix

Store the model weights/config/tokenizer under `<model>/resolve/main/` instead of
flat, so `cleanModelUrl()`'s appended `resolve/main/` resolves to the real files.
This mirrors HuggingFace's layout and requires no changes to `webllm.js`.

Changes:

1. `scripts/vendor-offline.sh` — download model files into
   `vendor/models/$MODEL_ID/resolve/main/` (via a new `MODEL_FILES_DIR` variable)
   and document why. The offline-config `model` path stays
   `/vendor/models/$MODEL_ID/` (WebLLM appends `resolve/main/`).

2. Local `vendor/` (git-ignored) — moved the already-downloaded files of
   `vendor/models/gemma3-1b-it-q4f16_1-MLC/` into its `resolve/main/` subdirectory
   so the existing bundle works without a 590 MB re-download. (Regenerated by the
   script on other machines.)

After the fix, all model artifacts are served where WebLLM looks for them
(verified via a local `python3 -m http.server` + `curl`: every
`.../resolve/main/...` path returns 200).

## Why this machine can't run it end-to-end

Kali's headless Chromium blocklists WebGPU and it cannot be overridden, so
`navigator.gpu` is undefined and `WebLLMProvider.supported()` short-circuits before
`CreateMLCEngine` runs. This was debugged by reading the vendored library and
reproducing its pure-JS URL logic in Node (no GPU required), plus verifying the
served file paths over HTTP. The remaining proof (real GPU inference) must happen
on a WebGPU-capable browser (e.g. Dan's MacBook Chrome).

## Verification steps for a WebGPU browser

1. `bash scripts/vendor-offline.sh` (or use the already-moved local `vendor/`).
2. `python3 -m http.server 8000`.
3. Open `http://localhost:8000`, Settings → DM, choose "In-browser model (WebLLM)".
4. "Test connection" → should report "Connection OK" (first load downloads ~590 MB
   of shards into the browser cache, so it is not instant).
