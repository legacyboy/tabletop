## Features implemented (all 8)

### 1. Kill chain (`attack_chain` in schema)
- Added per-scenario `attack_chain` array: ordered stages with `id`, `name`
  (executive-friendly plain language, e.g. "How they got in", "How it spread",
  "What they took" — NOT MITRE jargon), `symptom` (executive-facing description
  of what the group observes), and `revealed` (bool, default false).
- The DM's brief lists the hidden chain. The DM reveals a stage when the
  group's investigation plausibly uncovers it (`reveal_stage` in the DM JSON
  contract) and marks it contained when the group neutralizes it
  (`contain_stage`).
- Win condition becomes "contain all stages": `_checkEnd` fires a success when
  every stage is contained, even if numeric thresholds aren't all met.
- Engine tracks revealed/contained per stage in the session (persisted in
  serialize/restore) and feeds the current chain state to the DM each turn.

### 2. Metric rework (data-driven, per-scenario)
- Replaced `risk` with `attacker_progress` (0-100, the kill chain as a number).
- Added response-side metrics: `containment`, `eradication`, `recovery`,
  `security_posture`.
- Added `public_trust` (absorbs reputation + member_confidence).
- Kept `budget`, `regulator_confidence`. Dropped `morale` for the short
  scenario (still available for long ones).
- Engine is already data-driven (metrics come from `opening_state`); verified it
  handles any metric names generically.

### 3. Roll modifiers from defender actions
- Added `grantRollModifier(amount)` to the session; `rollModifier` is persisted
  in serialize/restore and consumed by the next roll.
- The DM brief explains the mechanic; the modifier nudges the roll (fed to the
  DM as an "adjusted roll"), it doesn't replace the DM's judgment.
- UI: "Play a defender capability (+3 next roll, -10 budget)" button in the play
  phase.

### 4. Soft round counter
- Turn tracking already exists; turn-triggered events inject pressure on a
  schedule (Bramble Badger `e5` fires on turn 6). No hard fail — timeout stays
  soft pressure.

### 5. Detection as a resource
- Added guidance to the DM brief + rules_of_play: the group cannot do
  everything at once, and activating monitoring costs budget. The DM enforces it.

### 6. Breach state
- Added discrete breach ladder `contained → active → escalated → exfiltrated`,
  derived from the attack chain (how many stages are revealed but not yet
  contained). Tracked in the session (persisted), fed to the DM each turn, and
  shown to players in the play phase.

### 7. Contained-stages report
- Closing report (both the in-app `renderReport` and the server `report.js`)
  shows which kill-chain stages the group contained and which they missed — a
  BDB-style debrief with plain-language stage names.

### 8. Random mode
- Added a `random` entry to `scenarios/registry.json` (`"random": true`).
- `scenarios.js` exports `randomScenarioShell()` (a valid minimal scenario) and
  `isRandomEntry()`.
- The engine handles a scenario with no pre-authored content: the DM system
  prompt includes a RANDOM MODE block that instructs the DM to generate the
  brief, opening state, goal, and events from a generic prompt.
- UI: "Random scenario (generated by the DM)" appears in the scenario selector.
- Server API (`api.js`) returns the shell for the random id.
